# Exact integer dot products for this NR model

Status: isolated native CUDA prototype implemented and benchmarked; rejected for production because it is slower. WebCuda and the production renderer are unchanged.

The read-only audit loaded and hash-verified all 153 tensors (147,683,778 packed bytes), validated their graph bindings, and scanned all 358 FP8 matrix operands in production layout. It examined all 143,831,040 matrix codes and 8,989,440 contiguous-K groups of 16. Statistics are generated by `scripts/analyze-model-structure.mjs`; the detailed local result is ignored `reports/model-structure.json`.

## Measurements

- 5.0301% of matrix codes represent zero.
- 0.1940% of 16-weight groups are all zero.
- No complete FP8 matrix operand repeats byte-for-byte.
- 98.8794% of 16-weight groups have an exact representation `w[j] = B[j] * 2^q`, with each signed coefficient's magnitude at most 127.
- Those groups account for 80.8724% of FP8 matrix multiply terms at 720p after weighting by graph row count (not measured GPU time).
- Every remaining group needs at most nine magnitude bits at its finest common exact power-of-two scale. Two signed byte components therefore suffice for the weights: `B = B_low + 128 * B_high`, where both components retain the original sign.
- The 720p graph contains 207.228 billion FP8 matrix multiply terms, plus attention and other operations not included in that count.

The audit factors out the greatest common power of two from each group of weight values represented as integer multiples of 1/512. It does not quantize or alter weights. Signed zeros need separate handling when reasoning about arithmetic semantics; the existing reference uses integer zero in its group sum.

## Proposed execution

For a compatible activation group, derive another lossless representation `a[j] = A[j] * 2^p`. Pack four signed coefficients per 32-bit word. Four packed integer dot products calculate the 16-term integer sum, and the common scale is applied once.

WebGPU exposes `dot4I8Packed`; CUDA exposes `__dp4a`. The repository's current WebCuda compiler search found no lowering for these operations. Supporting this path would require compiler/oracle support plus device verification. API availability alone does not prove efficient native lowering on every backend.

The key additional step is an exactness guard. NR's group operation is not ordinary matrix multiplication: it chooses an exponent based on the accumulator and the paired operands, truncates scaled terms, then rounds to half. A packed dot product followed by ordinary rounding is only interchangeable when those termwise truncations would discard nothing and the final sum is represented exactly.

For integer coefficients and product scale `q_total = p + q`, each product is an integer multiple of `2^q_total`. A sufficient condition for no product truncation at the actual F13 group exponent `E` is `q_total >= E - 13`. The accumulator must also be exactly representable at this quantum, or its original truncation must be handled explicitly. Bounds on exponents may provide a cheap sufficient guard without rescanning all operand pairs. The exact guard and sum-conversion bounds still need formalization and numerical verification, including cancellation, half subnormals, overflow, residual initialization, partitions, and signed zero.

Preserve every original 16-term group boundary, half-rounding point, partition merge, activation, and publication. Unsupported groups take the existing exact path. Do not regroup terms across rounding boundaries or assume that int8-representable weights alone imply an eligible operation.

The strongest opportunity is replacing the repeated exponent/product/truncation loops on eligible groups with hardware integer dots, not merely predecoding weights. Prefer packing activations at their producer or once per shared-memory tile; do not add another full-frame conversion pass by default. Any weight descriptors should remain compact rather than expanding into the previously rejected half-operand representation.

## What remains unknown

1. Activation-group representability across real image/history/conditioning inputs.
2. Frequency of the exactness guard passing once the running accumulator is included.
3. Divergence, packing, and register costs on the real GPU.
4. Actual native lowering and throughput of packed integer dots through the browser.
5. End-to-end improvement after attention and unaffected layers are included.

The experiment below measured activation and accumulator eligibility and implemented an isolated full-graph prototype. No model changes, pruning, resolution reduction, or approximate arithmetic were introduced. Performance work is now parked; the existing renderer is the accepted baseline, and this proposal is retained as a record rather than an active implementation plan.

References: [WGSL specification](https://www.w3.org/TR/WGSL/), [Chrome packed integer dot product support](https://developer.chrome.com/blog/new-in-webgpu-123).

## Prototype result

`scripts/integer-dot-variant.mjs` adds lossless shared-memory INT8 packing and CUDA `__dp4a` operations to the generated wide GEMMs in an isolated native build. It keeps the original exponent calculation and accumulator truncation. A fast group is admitted only if all eight outputs owned by an invocation qualify: both activation rows and four weight columns fit signed bytes, and the product scaling requires no right shift. Otherwise the original vector arithmetic runs. This tests a conservative implementation, not every possible integer-dot design.

The first generated prototype accidentally omitted packing because specialization had rewritten the insertion comment. Its timing was invalid and is superseded. The generator now requires the packing insertion point and an instrumented run confirmed actual fast-path execution.

An audit sampled thread zero of each workgroup at each 16-term stage, over the two synthetic full-model inputs. Across 134,091,776 repeated observations: both activation rows fit in 13.8008%, all four weight columns fit in 73.2571%, and all eight outputs pass the full guard in 4.9201%. This is a selected workgroup-lane sample, not an exhaustive proportion of model MACs or a real-scene dataset.

Final counters-disabled benchmark, RTX 5080, three untimed executions and ten timed samples per backend/resolution, ordinary median of the two middle samples:

| Resolution | Existing CUDA | Exact integer-dot prototype | Change |
|---|---:|---:|---:|
| 1280 x 720 | 157.262 ms | 179.662 ms | 14.24% slower |
| 1920 x 1080 | 331.990 ms | 377.883 ms | 13.82% slower |

Both native head buffers match byte-for-byte (8,257,536 and 17,694,720 bytes). Timings are CUDA events around the network only. Baseline and candidate ran sequentially on identical inputs; this is a bounded experiment, not a broad device/scene benchmark. The weak eligibility rate is consistent with packing and guard costs outweighing saved arithmetic. No browser compiler support or public experimental backend was added.

Reproduction: set `NR_INTEGER_DOT=1` and `NR_NATIVE_BUILD=build/native-intdot`, then run the native preparation and compilation scripts described in `native-cuda.md`. Unset `NR_DOT_AUDIT` for timings. `node scripts/benchmark-native-intdot.mjs` runs the prebuilt baseline and candidate and checks outputs. For eligibility counters, also set `NR_DOT_AUDIT=1` and use `NR_NATIVE_BUILD=build/native-intdot-audit` before generating/compiling; run that executable separately and do not use its instrumented timings as performance results. All generated binaries and model data remain in ignored build directories.
